Accessibility regressions are easy to ship and hard to notice. A refactor drops an `alt` attribute, a new icon button has no accessible name, a form field loses its label — and nothing in your test suite fails. By the time someone using a screen reader hits the problem, it's already in production.

The fix is to move accessibility checks into CI, where every pull request is scanned before it merges. a11y-fixer runs in GitHub Actions two ways: as the free, open-source CLI for a simple pass/fail gate, and as the **a11y-fixer-pro** Action, which can go further and open pull requests that fix the issues for you.

## Option 1: a free CI gate with the CLI

The quickest win is to fail the build when new violations appear. The MIT-licensed CLI needs no key and no configuration:

```yaml
name: Accessibility
on: pull_request

jobs:
  a11y-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx @a11y-fixer/cli check ./src
```

`check` scans your source and exits non-zero if it finds any WCAG 2.2 violations, so the job turns red on a regression. This is deterministic and completely free — but it only *reports* problems. Someone still has to open the editor and fix them.

## Option 2: automatic fix PRs with a11y-fixer-pro

The **a11y-fixer-pro** GitHub Action can apply the fixes and open a pull request for you. In `fix` mode it scans your source, applies every fix it can, and commits the result to a new branch with an annotated before/after summary:

```yaml
name: Accessibility
on: pull_request

jobs:
  a11y-fix:
    runs-on: ubuntu-latest
    permissions:
      contents: write        # push the fix branch
      pull-requests: write   # open the PR
    steps:
      - uses: actions/checkout@v4
      - uses: a11y-fixer/a11y-fixer-pro@v1
        with:
          mode: fix
          dir: ./src
          license-key: ${{ secrets.A11Y_FIXER_LICENSE_KEY }}
          anthropic-api-key: ${{ secrets.ANTHROPIC_API_KEY }}
          github-token: ${{ secrets.GITHUB_TOKEN }}
```

The Action has three modes: `check` (the default — a CI gate like the CLI), `scan` (report violations as a JSON output without failing), and `fix` (apply fixes and open a PR).

Note the `permissions` block. `fix` mode needs `contents: write` to push its branch and `pull-requests: write` to open the PR. Without them, the Action can scan but can't raise the pull request.

### What the fix PR looks like

a11y-fixer-pro never pushes to your base branch. A `fix` run creates a branch named `a11y-fixer/<timestamp>`, commits the changed files, and opens a normal pull request titled something like `a11y-fixer: fix 7 accessibility violation(s)`. You review the diff like any other PR and merge when you're happy. Nothing changes in your codebase without a human approving it.

## AI-assisted fixes

Many accessibility issues can be repaired by a deterministic rule — but some need a judgment call about what the content actually means. What should the `alt` text for this image say? What does this icon-only button do?

When you provide an `anthropic-api-key`, a11y-fixer-pro uses Claude to propose those fixes:

- **Image alt text** (WCAG 1.1.1) — a concise description generated from the surrounding code.
- **Icon-only button names** (WCAG 4.1.2) — an `aria-label` for buttons with no accessible name.
- **Form control names** (WCAG 1.3.1) — an `aria-label` for inputs, selects, and textareas missing a label.
- **Generic link text** (WCAG 2.4.4) — rewrites vague links like "click here" or "read more" into descriptive text.

Because these are judgment calls, they follow the same rule as every other change: they land in a pull request for a human to review, never directly on your base branch. Anything the model isn't confident it can change safely — non-generic link text, for example — is flagged for manual review with a note instead of being edited. And if you don't supply a key, those issues are simply reported so you can handle them yourself.

The free `@a11y-fixer/cli` stays fully deterministic and uses no AI at all. AI-assisted fixes are a feature of a11y-fixer-pro.

## Setting up the secrets

For `fix` mode with AI, add two repository secrets under **Settings → Secrets and variables → Actions**:

- `A11Y_FIXER_LICENSE_KEY` — your a11y-fixer-pro key.
- `ANTHROPIC_API_KEY` — your Anthropic API key, which enables the AI-assisted fixes.

`github-token` defaults to the built-in `${{ github.token }}`, so you usually don't need to set it — just grant the job the `permissions` shown above.

## Which should you use?

Start with the free CLI gate on every pull request — it costs nothing and stops regressions immediately. Add a11y-fixer-pro when you want the issues fixed for you instead of just flagged, especially the ones that need a human-quality `alt` or label.
